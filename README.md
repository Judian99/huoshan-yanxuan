# 火山严选 · 三个移动端前端原型

一个私人菜谱应用的三套信息架构原型。共用同一份纸张视觉语言、菜谱数据和交互内核。

## 打开方式

直接双击仓库根目录的 `index.html`，选择版本。也可以单独打开：

| 版本 | 入口 | 信息架构 |
|---|---|---|
| A · 餐牌厨房 | `demo-a/index.html` | 底部 Tab：餐单 / 菜谱 / 转盘 / 日历 |
| B · 手帐食谱本 | `demo-b/index.html` | 单页滚动 + 浮动索引坞 |
| C · 深夜灶台 | `demo-c/index.html` | 首页聚焦当前一餐 + 抽屉 + 印章悬浮按钮 |

无需构建。桌面可直接双击 `file://` 打开；手机（尤其 iPhone）见下方「方案B 的 iPhone 安装与数据持久化」。建议用手机浏览器，或把桌面窗口收窄到 480px 以内；三版也都做了桌面居中展示。

## 已实现的原型交互

- 菜谱：示例 12 道；搜索、按时段筛选、详情（食材/步骤/备注）、写新菜谱（名称、图片预览、适合餐次、用时、动态食材与步骤行、备注、必填校验）。
- 点菜：五时段；当天按当前时间预选时段；未来日期必须先选餐次；过去日期只读；可直接点某个餐格进入对应餐次。
- 转盘：SVG 转盘、按时段筛选、避开今天已点的菜、最多 8 段候选、旋转结果票据、结果可加进指定餐次。
- 日历：月切换、红点、今天圆环、选中日、回到今天；选中日期驱动全站日期；支持跨月/历史翻看。
- 复制：把某天菜单复制到之后 7 天中的任意一天，可勾选餐次，支持撤销。
- 反馈：底部印章 Toast（带撤销）、弹层可叠层（如菜谱库 → 菜谱详情）、键盘焦点管理与 `prefers-reduced-motion` 支持。

## 工程说明

```
index.html            三版入口
shared/
  base.css            设计令牌、纸张纹理、通用控件、弹层/转盘/日历
  data.js             示例菜谱、相对日期菜单、五时段与内存操作
  wheel.js            SVG 转盘绘制与旋转
  kit.js              日期条、餐次选择、选菜、详情、表单、复制、Toast
  store.js            IndexedDB 持久化、图片压缩入库、导出/导入（方案B 使用）
demo-a/               餐牌厨房
demo-b/               手帐食谱本（含 manifest / sw.js / icons，可装成 PWA）
demo-c/               深夜灶台
```

全部使用 classic script + 相对路径，不依赖外网字体、图片或接口。

## 方案B 的 iPhone 安装与数据持久化

方案B 已落地为一个「本地化 Web 应用（PWA）」：数据（菜谱、餐单、照片）只存在用户自己的手机里，服务器只托管应用外壳，不接触任何私人数据。

**为什么不能直接打开 HTML：** iPhone 上的 Safari 不能直接打开本地 `file://` 的 HTML（Files 预览不执行 JavaScript、不加载外部样式），必须通过一个 HTTPS 地址访问。

**第一步：用一个 HTTPS 地址托管（任选其一，均免费）**

- GitHub Pages：`git init` 后推到仓库，仓库 Settings → Pages 开启，得到 `https://用户名.github.io/仓库名/demo-b/`。
- Cloudflare Pages / Vercel / Netlify：连接仓库或直接 `pages deploy` 部署，自动 HTTPS。
- 本地预览可在仓库根目录执行 `python3 -m http.server 8000`，用同一局域网手机访问 `http://电脑IP:8000/demo-b/`（注意：Service Worker 的完整能力需 HTTPS，localhost 除外）。

**第二步：装到 iPhone 主屏幕**

1. 用 Safari 打开上面的 HTTPS 地址（必须是 Safari，第三方浏览器在 iOS 上能力受限）。
2. 点底部「分享」按钮 → 「添加到主屏幕」（iOS 26 若出现「打开为 Web App」开关，请打开）→ 「添加」。
3. 之后从主屏幕图标进入，即为无地址栏的独立 App 形态。

**第三步：离线与数据**

- 首次需**联网打开一次**，让 Service Worker 把应用外壳缓存下来；之后飞行模式也能完整使用。
- 数据持久化说明：普通 Safari 网页对 IndexedDB/localStorage 有「7 天不互动即清理」的策略；**加到主屏幕的 Web App 豁免该清理**，且 iOS 17+ 会自动授予持久化存储（应用启动时也会主动调用 `navigator.storage.persist()` 请求）。
- 照片会先在本地压缩（长边 ≤1000px、JPEG 0.72）再存入 IndexedDB，单张约 50–150KB。
- 兜底：页面底部有「导出备份 / 导入恢复」。导出会得到一个含全部菜谱（照片以 base64 内嵌）与餐单的 JSON 文件，建议定期导出到「文件」或 iCloud；清数据或换手机后用「导入恢复」即可还原。

**已知边界：** 存储配额按设备磁盘计算（一般数百 MB 起）；用户手动「清理网站数据」、卸载主屏幕 App 仍会删除本地数据，这正是需要定期导出备份的原因。需要跨设备同步则要上云端（另立方案）。

## 各版本能力范围

- **方案B（手帐食谱本）已落地持久化**：菜谱、餐单、照片通过 IndexedDB 保存，刷新/重开不丢；支持 Service Worker 离线、主屏幕安装、导出/导入备份。
- 方案A、方案C 仍为内存原型：刷新回到示例数据（它们未接入 `store.js`，行为保持不变）。
- 三版通用：已有菜谱的「编辑 / 删除」仍保留入口，提示演示版未接入（下一期再做）。
- 暂无账号、后端、云同步、音效。

## 建议验收路径

1. 首页看今日五餐，切到明天，点「点一道」，确认没有自动预选餐次。
2. 切到昨天，确认只读、没有加点入口。
3. 转盘抽一道，加进指定餐次，再用「撤销」恢复。
4. 日历选一个未来日期，看这天餐单和红点。
5. 写一道新菜，保存后回到菜谱列表确认出现。
6. 复制某天菜单到另一天，再撤销。
